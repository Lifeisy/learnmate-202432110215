# Git 协作与持续集成

## 分支模型

常见的轻量分支模型是：main 保持可发布，feature/* 开发单个功能，fix/* 修复缺陷，release/* 准备版本。每个功能从最新的 main 切出，完成后通过 Pull Request 合并，合并后删除临时分支。

分支粒度要与任务粒度一致。一个分支同时改登录、前端和数据库，评审时很难判断风险。提交信息应说明“做了什么、为什么”，例如 feat(auth): add JWT login endpoint，而不是 update 或 fix bug。

## 冲突的成因与解决

冲突发生在两个分支修改了同一文件的同一区域，Git 无法自动判断保留哪一版。解决冲突不是简单选择“我的”或“对方的”，而是理解两边意图后合并出正确结果，并运行测试验证。

典型流程是：在 feature 分支执行 git merge main，打开冲突文件，删除 <<<<<<<、=======、>>>>>>> 标记，保留并整合双方修改，git add 标记已解决，git commit 完成合并。冲突解决后必须重新构建和测试，不能只看文件是否能打开。

## Pull Request 与 Code Review

PR 应包含变更目的、主要改动、验证方式、风险和截图。评审者关注：是否符合需求、是否有越权或注入风险、异常边界是否覆盖、测试是否有效、是否引入敏感信息。作者不能以“AI 生成的”为由跳过自测。

AI 可以辅助生成 PR 摘要、提示潜在的空指针或未处理异常，但 AI 评审不是最终责任方。人工评审要核对业务语义和安全边界，并对合并结果负责。

## 持续集成

CI 在每次 push 和 PR 时自动执行构建、测试和静态检查，尽早发现“在我电脑上能跑”的问题。GitHub Actions 的基本结构是 on、jobs、runs-on、steps。Java 项目通常使用 actions/setup-java 安装 JDK，缓存 Maven 依赖，然后执行 mvn -B test。

前端任务使用 actions/setup-node 安装 Node，执行 npm ci 和 npm run build。后端与前端可以并行，也可以在前端构建后把 dist 复制到后端静态目录再做整包构建。

CI 失败时必须修复，而不是反复重跑。对偶发失败要定位根因；对密钥等敏感信息使用 Repository Secrets，绝不要写进 workflow 文件。分支保护可以要求 PR 至少一人评审且 CI 通过后才能合并。
