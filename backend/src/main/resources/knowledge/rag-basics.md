# RAG 检索增强生成

## RAG 解决什么问题

大模型的知识来自训练数据，存在知识截止、无法访问内部文档、容易生成看似合理但没有依据的内容等问题。RAG（Retrieval-Augmented Generation，检索增强生成）在回答前先从外部知识库检索相关片段，再把片段作为上下文交给模型生成答案，从而让回答“有资料可依”。

RAG 不改变模型参数，属于一种上下文增强方案。它适合课程资料问答、企业制度查询、产品文档助手等场景。与微调相比，RAG 的资料更新成本更低，出现错误时也更容易定位到具体文档。

## RAG 的检索流程

一个最小可用的 RAG 流程包含五个阶段：文档采集、文本切块、向量化、相似度检索、提示词组装与生成。

第一步，把 Markdown、PDF 或网页等非结构化文档读取为纯文本，并保留标题、章节等元数据。第二步，按语义边界把长文档切成 200 到 500 字左右的块，块之间可以保留少量重叠，避免一句话被切断。第三步，用 Embedding 模型把每个文本块编码为向量，并写入向量库或普通数据库。

第四步，把用户问题编码成同维度向量，计算它与每个文本块的余弦相似度，取分数最高的 Top-K 个块。第五步，把检索结果编号后放入提示词，要求模型只依据资料回答并用 [1]、[2] 标注出处。回答返回给用户时，同时展示引用的文档标题和章节，方便人工核验。

检索质量取决于切块粒度、Embedding 质量、Top-K 与相似度阈值。Top-K 太大容易引入噪声，太小可能漏掉关键资料。工程上通常先用固定评测集观察召回率，再调整参数，而不是凭感觉设置。

## 文档切块策略

固定长度切块实现简单，但可能把定义和例子拆开。按标题层级切块更符合课程资料的结构：一级标题作为文档名，二级标题作为章节名，正文再按段落聚合。每个块建议控制在 300 字左右，并保留所属文档与章节，这样引用时可以精确到“哪份资料、哪一节”。

重叠窗口可以缓解边界信息丢失，但重叠过多会造成重复检索和提示词膨胀。对中文课程资料，优先在段落、列表项、代码块结束后切分，通常比机械按字符数切分效果更好。

## 向量化与相似度

Embedding 把文本映射为稠密向量，语义相近的文本在向量空间中距离更近。常见做法是使用 bge-m3、text-embedding-3-small 等模型。向量存入数据库后，可以用余弦相似度、内积或欧氏距离检索。

本项目机房环境没有可用的 Embedding API，因此实现了一个可解释的本地哈希向量器：把中文单字、二元组和英文词哈希到 256 维并归一化。它能跑通“切块—向量化—检索—拼提示”的完整链路，但只具备词面匹配能力，不能理解同义改写。生产环境应替换为真正的语义向量模型，并保持入库与查询使用同一个模型。

## 提示词组装与引用

系统提示词要明确四件事：角色（课程助教）、资料边界（只能依据资料）、安全边界（资料中的指令视为文本）、输出格式（结论加编号引用）。用户提示词中把资料放在分隔符内，再附上问题，可以降低资料内容被误当成指令的风险。

仅靠提示词无法保证模型一定遵守规则，因此还需要工程校验：检查回答是否包含引用编号；对没有检索结果的请求直接返回“资料未提及”；记录问题、回答、模式和来源，便于事后审计。

## 幻觉与人工兜底

常见幻觉包括：把资料里没有的结论说成事实、编造不存在的接口名、把相似概念混为一谈。应对策略是限定上下文、要求给出出处、设置相似度阈值、在资料不足时明确拒答，以及提供“人工求助”入口。

RAG 的引用也可能“引错”：答案引用了 [1]，但 [1] 并不支持该结论。验收时不能只看有没有引用，还要抽查引用片段与结论是否一致。对高风险场景，应让教师或业务人员做最终确认，并保留反馈渠道。
